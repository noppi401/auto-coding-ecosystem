▲ Auto Coding Ecosystem

要件定義 → 設計 → タスク分解 → 実装 → レビュー → 修正 → PR 作成 → マージ までを、複数の AI エージェントが連携して自動化するローカル実行型パイプライン。このページは、はじめて触る方向けに「仕組み」と「使い方」をまとめたガイドです。

1. これは何？

あなたが日本語で指示を渡すと、ツールが自動で次のことを行います。

  • 計画（Phase 1）: 指示から要件定義・設計書を作り、品質を別エージェントが採点。合格したら実装タスクへ分解し、GitHub Issue を起票します。
  • 実装（Phase 2）: タスクごとにブランチを切ってコードを生成 → PR を作成 → ビルド/テストとレビューを回して修正 → 承認されたらマージし、Issue を閉じます。

利用する AI は Claude を基本に、利用上限に達したら Codex / Gemini へ自動で切り替えられます。すべてローカルの CLI（claude / gh など）を呼び出して動作します。

2. エージェント構成

各エージェントは共通基盤 BaseAgent（LLM 呼び出し・フォールバック・利用上限検知）を継承します。司令塔の Orchestrator がこれらを順に呼び出し、状態は .ecosystem/state.json に保存されます。

3. 処理の流れ

指示の入力からマージまで、エージェントは次のようにバトンを渡していきます。

▶ Phase 1 ： 計画（要件 → 設計 → タスク → Issue）
指示入力自然言語 / エディタ複数行
→
Requirements要件生成＋採点ループ
→
Design設計生成＋採点ループ
→
TaskDecompタスク分解＋複雑度
→
承認 → Issue 起票一覧をプレビュー承認
※ 採点が閾値未満なら、要件/設計はそれぞれ自動で修正ループ。結果は .ecosystem/*.md に保存。
▶ Phase 2 ： 実装（タスクごとに 1 件ずつ）
ブランチ作成GitHubAgent
→
Codingコード生成→コミット→PR
→
ビルド/テストtsc / npm test（決定論）
→
Review (+Codex)差分レビュー
→
Fixblocking を修正
→
マージ→Issue closeworktree 同期
※ Review → Fix は承認されるまで最大 MAX_REVIEW_ITERATIONS 回ループ。常に「アクティブな Issue/PR は 1 つ」。
利用上限（usage limit）に達した場合は FALLBACK_LLM_PROVIDER へ自動切替、または後から --retry-failed で再開できます。

4. システムの内部構造（SDK / CLI と実行の仕組み）

各エージェントが「どうやって AI を呼び出し、エコシステムとして連携しているか」の技術的な解説です。

4.1 共通基盤 BaseAgent と呼び出し方式

すべてのエージェント（RequirementsAgent / DesignAgent / CodingAgent / ReviewAgent …）は BaseAgent を継承します。BaseAgent.invoke() が provider を解決し、対応するメソッド（invokeClaude / invokeCodex / invokeGemini / invokeLocal）へ振り分けます。

本ツールは各プロバイダーの公式 CLI をサブプロセスとして起動し、プロンプトを 標準入力（stdin）で渡して結果を受け取る方式です（ローカル LLM のみ OpenAI 互換 HTTP API を直接呼び出し）。特定言語の SDK には依存せず、ローカルにインストール済みの CLI 認証・設定をそのまま利用します。Windows のコマンド長制限やクォート事故を避けるため、プロンプトは引数ではなく stdin、system prompt は一時ファイル（--system-prompt-file）で渡します。

4.2 プロバイダー別の呼び出し

provider呼び出し方法モデル指定応答形式
Claude
既定		 claude -p --model <id> --output-format json --dangerously-skip-permissions（プロンプトは stdin）。RESUME_AGENT_SESSIONS=true 時は --continue <session_id> で会話を継続。 PLANNING_CLAUDE_MODEL / IMPLEMENTATION_CLAUDE_MODEL（無ければ CLAUDE_MODEL） JSON（result / session_id / is_error）
Codex codex exec --skip-git-repo-check --sandbox <mode> --output-last-message <file>。最終メッセージをファイルから回収。 CODEX_MODEL / CODEX_INTELLIGENCE（reasoning effort） 最終メッセージ（テキスト）
Gemini gemini -m <id> -o json -p（プロンプトは stdin。Windows のコマンド長制限を回避）。 PLANNING_GEMINI_MODEL / IMPLEMENTATION_GEMINI_MODEL（無ければ GEMINI_MODEL、既定 gemini-2.5-flash） JSON（content/result/text/candidates を順に解釈。Markdown コードブロック等は robustJsonParse でフォールバック解析）
Local OpenAI 互換エンドポイント {LOCAL_LLM_URL}/chat/completions へ HTTP POST（Ollama / LM Studio 等）。 LOCAL_LLM_MODEL JSON（choices[].message.content）
Gemini を使うには：gemini CLI をインストール・認証し、.env に GEMINI_API_KEY を設定します。provider はウィザード（実行AI 第1/第2候補）、または --provider gemini / --fallback-provider gemini で選択。モデルはウィザードの「Gemini モデル」入力、または --gemini-model <id> / 環境変数で指定します。利用上限（QUOTA_EXHAUSTED など）を検知すると、利用上限エラーとして扱いフォールバックします。

4.3 ルーティング・フォールバック・堅牢性

  • 役割振り分け: エージェント名が IMPLEMENTATION_AGENTS（既定 CodingAgent,FixAgent）に含まれれば implementation ルート、それ以外は planning ルートとして provider / モデルを解決。
  • per-task モデル上書き: TASK_MODEL_ROUTING 有効時、タスクの複雑度に応じた Claude モデルを setModelOverride() で実装系エージェントに適用（env を汚さない）。
  • フォールバック: 呼び出しが利用上限に達すると当該 provider を「上限到達」として記録し、FALLBACK_LLM_PROVIDER へ自動切替。AI_TOKEN_MODE を特定 provider に固定した場合はフォールバックせず停止し、後で --retry-failed で再開。
  • 応答の堅牢パース: robustJsonParse が Markdown コードブロック・二重エスケープ・テンプレートリテラル・文字列内の生改行などを吸収して JSON 化。
  • タイムアウト: 各 CLI 呼び出しは AGENT_COMMAND_TIMEOUT_MS（既定 15 分）で打ち切り。

4.4 連携・状態・検証

  • GitHubAgent: gh CLI と git を用い、リポジトリ作成 / ブランチ / コミット / Issue / PR / マージ / コメントを実行。さらに .ecosystem/worktrees/... の作業ツリーで tsc --noEmit や npm test を回し、結果を「決定論的ゲート」としてレビューに反映。
  • StateManager: 進行状態を .ecosystem/state.json へ逐次保存（要件・設計・タスク・各 PR/Issue・エージェントの session_id 等）。中断後の Resume はここから復元。
  • イベントバス（src/events.ts）: Orchestrator の進捗（phase 変化 / タスク更新 / ログ / タスク承認）を Ink UI へ配信。UI と実行ロジックは疎結合。

6. 使い方

対話モードで起動（おすすめ）

npm run dev
より簡単に：一度 npm run build && npm link しておくと、どこからでも ace で起動できます（ace status / ace phase2 --retry-failed など、引数は npm run dev -- と同じ）。

ホームメニューから選びます。

  • New request — 新しい依頼を作成（新規リポジトリ or 既存リポジトリ改修）
  • Run from Issue — 既存リポジトリの open Issue を選んで実行（複数選択・全件可）
  • Resume Phase 2 — 途中で止まったコーディングループを再開
  • Phase 1 only — 計画だけ実行して Issue を起票し停止
  • Show status — 現在の進捗（進捗バー・経過時間・PR/Issue リンク）を表示
ウィザードの選択（プロバイダー・モデル・フェーズなど）は .ecosystem/wizard-defaults.json に保存され、次回起動時に初期値として復元されます。実行状態は画面ヘッダーに ⏸ 入力待ち / ● 実行中 / ✓ 完了 と常時表示されます。

コマンドラインで実行

# 新規リポジトリを作って計画→実装まで自動実行
npm run dev -- start --instruction-file ./instruction.txt --repo-name my-repo --auto

# 既存リポジトリを改修
npm run dev -- modify --target-repo owner/repo --instruction-file ./change.txt --auto

# 既存 Issue を直接実行（複数可）
npm run dev -- modify --target-repo owner/repo --issue-number 123,124 --auto

# Phase 2 だけ実行 / 失敗タスクを再試行
npm run dev -- phase2 --retry-failed

# 進捗を確認
npm run dev -- status
長い日本語指示は、文字化けを避けるため --instruction-file での受け渡しを推奨します（対話モードでは「エディタで複数行入力」も選べます）。

モデルを指定する

npm run dev -- phase2 --planning-model claude-haiku-4-5-20251001
npm run dev -- phase2 --impl-model claude-sonnet-4-6
npm run dev -- start ... --provider codex --codex-model gpt-5.5 --codex-intelligence high
npm run dev -- start ... --provider gemini --gemini-model gemini-2.5-flash

CLI 引数は .env より優先されます。Planning（計画系）は安価なモデル、Implementation（実装系）はやや高性能なモデル、という使い分けが基本です。

7. トークン削減オプション

いずれも既定は無効（現行挙動を維持）で、環境変数で有効化する opt-in 方式です。

環境変数既定効果
TASK_MODEL_ROUTINGopt-in false タスクの複雑度に応じて実装モデルを自動選択（low→haiku / medium→sonnet / high→opus）。ユーザー指定モデルは「上限」として尊重。
REPO_CONTEXT_SUMMARYopt-in false 既存リポジトリのコンテキストを一度だけ要約し、要件/設計/タスク分解で再利用。
IMPL_DOC_RELEVANCEopt-in false コード生成時、要件・設計書をタスク関連セクションに絞り込む。
PR_DIFF_MAX_CHARS 30000 レビュー/修正に渡す PR diff を上限でトリミング。lockfile は既定で除外。0 で無効。

9. つまずきやすいポイント

  • PowerShell で npm / npx が実行ポリシーに止められる場合は npm.cmd / npx.cmd を使う。
  • 状態は .ecosystem/state.json に保存。途中で止めても Resume Phase 2 で再開できる。
  • 確認用 worktree（.ecosystem/worktrees/...）に未コミット変更があると、安全のため自動同期が止まる。
  • Claude の利用上限に達したら、上限リセット後に npm run dev -- phase2 --retry-failed で再開。
