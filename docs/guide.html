▲ Auto Coding Ecosystem

要件定義 → 設計 → タスク分解 → 実装 → レビュー → 修正 → PR 作成 → マージ までを、複数の AI エージェントが連携して自動化するローカル実行型パイプライン。このページは、はじめて触る方向けに「仕組み」と「使い方」をまとめたガイドです。 A locally-executed pipeline where multiple AI agents collaborate to automate: requirements → design → task decomposition → implementation → review → fixing → PR creation → merging. This page is a guide for first-time users covering how it works and how to use it.

1. これは何？What is this?

あなたが指示を渡すと、ツールが自動で次のことを行います。When you give an instruction, the tool automatically does the following.

  • 計画（Phase 1）Planning (Phase 1): 指示から要件定義・設計書を作り、品質を別エージェントが採点。合格したら実装タスクへ分解し、GitHub Issue を起票します。Creates requirements and design documents from your instruction; a separate agent scores quality. Once approved, decomposes into implementation tasks and creates GitHub Issues.
  • 実装（Phase 2）Implementation (Phase 2): タスクごとにブランチを切ってコードを生成 → PR を作成 → ビルド/テストとレビューを回して修正 → 承認されたらマージし、Issue を閉じます。Creates a branch per task, generates code → creates a PR → runs build/test and review cycles with fixes → merges when approved and closes the Issue.

利用する AI は Claude を基本に、利用上限に達したら Codex / Gemini へ自動で切り替えられます。すべてローカルの CLI（claude / gh など）を呼び出して動作します。The primary AI is Claude; when usage limits are reached the system automatically switches to Codex or Gemini. Everything runs by invoking locally-installed CLI tools (claude, gh, etc.).

2. エージェント構成Agent Architecture

各エージェントは共通基盤 BaseAgent（LLM 呼び出し・フォールバック・利用上限検知）を継承します。司令塔の Orchestrator がこれらを順に呼び出し、状態は .ecosystem/state.json に保存されます。Each agent extends the common BaseAgent (LLM invocation, fallback, usage-limit detection). The Orchestrator calls them in sequence; state is saved to .ecosystem/state.json.

4. システムの内部構造（SDK / CLI と実行の仕組み）Internals (SDK / CLI and Execution Mechanism)

各エージェントが「どうやって AI を呼び出し、エコシステムとして連携しているか」の技術的な解説です。A technical explanation of how each agent calls AI and how they work together as an ecosystem.

4.1 共通基盤 BaseAgent と呼び出し方式Common base BaseAgent and invocation method

すべてのエージェント（RequirementsAgent / DesignAgent / CodingAgent / ReviewAgent …）は BaseAgent を継承します。BaseAgent.invoke() が provider を解決し、対応するメソッド（invokeClaude / invokeCodex / invokeGemini / invokeLocal）へ振り分けます。All agents (RequirementsAgent / DesignAgent / CodingAgent / ReviewAgent …) extend BaseAgent. BaseAgent.invoke() resolves the provider and dispatches to the corresponding method (invokeClaude / invokeCodex / invokeGemini / invokeLocal).

本ツールは各プロバイダーの公式 CLI をサブプロセスとして起動し、プロンプトを 標準入力（stdin）で渡して結果を受け取る方式です（ローカル LLM のみ OpenAI 互換 HTTP API を直接呼び出し）。特定言語の SDK には依存せず、ローカルにインストール済みの CLI 認証・設定をそのまま利用します。Windows のコマンド長制限やクォート事故を避けるため、プロンプトは引数ではなく stdin、system prompt は一時ファイル（--system-prompt-file）で渡します。This tool launches each provider's official CLI as a subprocess, passing prompts via stdin and reading back results (local LLMs use the OpenAI-compatible HTTP API directly). No language-specific SDK is required; the tool uses the auth and config of locally-installed CLIs. To avoid Windows command-length limits and quoting issues, prompts go via stdin and system prompts via a temp file (--system-prompt-file).

4.3 ルーティング・フォールバック・堅牢性Routing, Fallback, and Robustness

  • 役割振り分けRole routing: エージェント名が IMPLEMENTATION_AGENTS（既定 CodingAgent,FixAgent）に含まれれば implementation ルート、それ以外は planning ルートとして provider / モデルを解決。If the agent name is in IMPLEMENTATION_AGENTS (default: CodingAgent,FixAgent), it uses the implementation route; otherwise the planning route for provider/model resolution.
  • per-task モデル上書きPer-task model override: TASK_MODEL_ROUTING 有効時、タスクの複雑度に応じた Claude モデルを setModelOverride() で実装系エージェントに適用（env を汚さない）。When TASK_MODEL_ROUTING is enabled, the Claude model matching the task's complexity is applied to implementation agents via setModelOverride() (without polluting env vars).
  • フォールバックFallback: 呼び出しが利用上限に達すると当該 provider を「上限到達」として記録し、FALLBACK_LLM_PROVIDER へ自動切替。AI_TOKEN_MODE を特定 provider に固定した場合はフォールバックせず停止し、後で --retry-failed で再開。When a call hits the usage limit, that provider is flagged as exhausted and the system auto-switches to FALLBACK_LLM_PROVIDER. If AI_TOKEN_MODE is locked to a specific provider, the system stops rather than falling back; resume with --retry-failed.
  • 応答の堅牢パースRobust response parsing: robustJsonParse が Markdown コードブロック・二重エスケープ・テンプレートリテラル・文字列内の生改行などを吸収して JSON 化。robustJsonParse handles Markdown code blocks, double-escaped strings, template literals, and literal newlines inside strings, converting them to valid JSON.
  • タイムアウトTimeout: 各 CLI 呼び出しは AGENT_COMMAND_TIMEOUT_MS（既定 15 分）で打ち切り。Each CLI call is terminated after AGENT_COMMAND_TIMEOUT_MS (default 15 min).

4.4 連携・状態・検証Integration, State, and Verification

  • GitHubAgent: gh CLI と git を用い、リポジトリ作成 / ブランチ / コミット / Issue / PR / マージ / コメントを実行。さらに .ecosystem/worktrees/... の作業ツリーで tsc --noEmit や npm test を回し、結果を「決定論的ゲート」としてレビューに反映。Uses gh CLI and git for repo creation / branch / commit / Issue / PR / merge / comments. Also runs tsc --noEmit and npm test in the .ecosystem/worktrees/... working tree; results feed into review as a "deterministic gate."
  • StateManager: 進行状態を .ecosystem/state.json へ逐次保存（要件・設計・タスク・各 PR/Issue・エージェントの session_id 等）。中断後の Resume はここから復元。Saves progress incrementally to .ecosystem/state.json (requirements, design, tasks, PR/Issue numbers, agent session_ids, etc.). Resume after interruption restores from here.
  • イベントバスEvent bus (src/events.ts): Orchestrator の進捗（phase 変化 / タスク更新 / ログ / タスク承認）を Ink UI へ配信。UI と実行ロジックは疎結合。Distributes Orchestrator progress (phase changes / task updates / logs / task approval) to the Ink UI. UI and execution logic are loosely coupled.

6. 使い方Usage

対話モードで起動（おすすめ）Launch in interactive mode (recommended)

npm run dev
より簡単にEven simpler: 一度 npm run build && npm link しておくと、どこからでも ace で起動できます（ace status / ace phase2 --retry-failed など、引数は npm run dev -- と同じ）。Run npm run build && npm link once, then you can launch ace from any directory (ace status / ace phase2 --retry-failed etc.; args are the same as npm run dev --).

ホームメニューから選びます。Choose from the home menu:

  • New request — 新しい依頼を作成（新規リポジトリ or 既存リポジトリ改修）Create a new request (new repository or modify existing)
  • Run from Issue — 既存リポジトリの open Issue を選んで実行（複数選択・全件可）Select open Issues from an existing repository to run (multi-select or all)
  • Resume Phase 2 — 途中で止まったコーディングループを再開Resume an interrupted coding loop
  • Phase 1 only — 計画だけ実行して Issue を起票し停止Run planning only, create Issues, then stop
  • Show status — 現在の進捗（進捗バー・経過時間・PR/Issue リンク）を表示Display current progress (progress bar, elapsed time, PR/Issue links)
ウィザードの選択（プロバイダー・モデル・フェーズなど）は .ecosystem/wizard-defaults.json に保存され、次回起動時に初期値として復元されます。実行状態は画面ヘッダーに ⏸ 入力待ち / ● 実行中 / ✓ 完了 と常時表示されます。Wizard selections (provider, model, phase, etc.) are saved to .ecosystem/wizard-defaults.json and restored as defaults on next launch. Run state is always shown in the header as ⏸ waiting / ● running / ✓ done.

コマンドラインで実行Command-line usage

# 新規リポジトリを作って計画→実装まで自動実行# Create a new repo and auto-run planning through implementation
npm run dev -- start --instruction-file ./instruction.txt --repo-name my-repo --auto

# 既存リポジトリを改修# Modify an existing repository
npm run dev -- modify --target-repo owner/repo --instruction-file ./change.txt --auto

# 既存 Issue を直接実行（複数可）# Run existing Issues directly (multiple allowed)
npm run dev -- modify --target-repo owner/repo --issue-number 123,124 --auto

# Phase 2 だけ実行 / 失敗タスクを再試行# Run Phase 2 only / retry failed tasks
npm run dev -- phase2 --retry-failed

# 進捗を確認# Check progress
npm run dev -- status
長い指示は、文字化けを避けるため --instruction-file での受け渡しを推奨します（対話モードでは「エディタで複数行入力」も選べます）。For long instructions, passing them via --instruction-file is recommended to avoid encoding issues (in interactive mode you can also select "Multi-line editor input").

モデルを指定するSpecifying models

npm run dev -- phase2 --planning-model claude-haiku-4-5-20251001
npm run dev -- phase2 --impl-model claude-sonnet-4-6
npm run dev -- start ... --provider codex --codex-model gpt-5.5 --codex-intelligence high
npm run dev -- start ... --provider gemini --gemini-model gemini-2.5-flash

CLI 引数は .env より優先されます。Planning（計画系）は安価なモデル、Implementation（実装系）はやや高性能なモデル、という使い分けが基本です。CLI args override .env. The typical pattern is a cheaper model for Planning and a slightly more capable model for Implementation.

9. つまずきやすいポイントCommon Pitfalls

  • PowerShell で npm / npx が実行ポリシーに止められる場合は npm.cmd / npx.cmd を使う。If PowerShell blocks npm / npx due to execution policy, use npm.cmd / npx.cmd.
  • 状態は .ecosystem/state.json に保存。途中で止めても Resume Phase 2 で再開できる。State is saved to .ecosystem/state.json. Even if interrupted, you can resume with Resume Phase 2.
  • 確認用 worktree（.ecosystem/worktrees/...）に未コミット変更があると、安全のため自動同期が止まる。If the verification worktree (.ecosystem/worktrees/...) has uncommitted changes, auto-sync is paused for safety.
  • Claude の利用上限に達したら、上限リセット後に npm run dev -- phase2 --retry-failed で再開。After Claude's usage limit resets, resume with npm run dev -- phase2 --retry-failed.
